# Financial Mutation Authorization and Ownership Matrix

Audit scope: source-level route/controller/service review for Bulk Action 3 (Wallet and Payment Integrity). This document records the route-to-service boundaries and existing regression coverage; it is not a claim that live provider contracts or production infrastructure have been independently verified.

## Customer financial mutations

| Operation | Route / name | Route guard | Service boundary and required invariant | Regression coverage |
|---|---|---|---|---|
| Create funding intent | `POST /wallet/funding-intents` — `wallet.funding-intents.create` | `auth`, throttle | `PaymentFundingController::createIntent` selects the authenticated user's NGN wallet; intent reference/idempotency and amount/tier limits enforced in the payment intent/funding services. | `PaymentIntentIdempotencyTest`, `PaymentFundingWorkflowTest`, `FinancialMutationAuthenticationTest` |
| Checkout return | `GET /wallet/funding/return` — `wallet.funding.return` | throttle; intentionally reachable as a gateway return URL | Return handler is not the settlement authority; verified gateway webhook/service is responsible for crediting. Return path must not independently credit a wallet. | `PaymentFundingWorkflowTest` |
| Submit manual deposit | `POST /wallet/manual-deposits` — `wallet.manual-deposits.submit` | `auth`, throttle | Controller resolves wallet for current user; `ManualDepositSubmissionService` rejects wallet/user mismatch, bounds amount, validates evidence fingerprint, flags duplicate evidence; unique transfer reference and evidence-fingerprint constraints protect races. | `ManualDepositWorkflowTest`, `FinancialMutationAuthenticationTest` |
| Request refund | `POST /wallet/refund-requests` — `wallet.refund-requests.create` | `auth`, throttle | Refund is attached to an owned payment intent; request idempotency and status/amount rules enforced by `PaymentRefundService`. Requesting a refund does not itself send money. | `PaymentRefundWorkflowTest`, `PaymentRefundMariaDbConcurrencyTest`, `FinancialMutationAuthenticationTest` |
| View one refund | `GET /wallet/refund-requests/{refund}` | `auth`, throttle | Query is scoped through payment intent → wallet → authenticated user; foreign refund IDs must not disclose data. | `PaymentRefundWorkflowTest` |
| P2P transfer | `POST /wallet/transfers` — `wallet.transfers.store` | `auth`, throttle | `PeerWalletTransferService`: PIN verification at controller; rejects self-transfer; validates amount/key; locks both wallets in deterministic ID order; rechecks idempotency after locks; balanced ledger debit/credit and unique-key race recovery. | `PeerWalletTransferTest`, `PeerWalletTransferMariaDbConcurrencyTest`, `FinancialMutationAuthenticationTest` |
| Add/remove bank beneficiary | `POST/DELETE /wallet/bank-transfer/beneficiaries...` | `auth`, throttle | `BankPayoutService` verifies ownership and account data; another user's beneficiary cannot be removed/reused; deletion is blocked where payout history requires retention. | `BankPayoutSafetyTest` |
| Request bank payout | `POST /wallet/bank-transfer` — `wallet.bank-transfer.store` | `auth`, throttle | PIN/lockout checked before debit; beneficiary must belong to caller and be verified; amount/key validated; idempotency payload hash checked; reservation/debit happens once; uncertain provider outcome is held for reconciliation, never blindly retried. | `BankPayoutSafetyTest`, `BankPayoutMariaDbConcurrencyTest`, `FinancialMutationAuthenticationTest` |
| Provision virtual account | `POST /wallet/virtual-accounts` — `wallet.virtual-accounts.provision` | `auth`, throttle | `UserVirtualAccountController/Service` scopes assignment to current user and uses a claim/recovery path before dispatch; disabled by default unless explicitly configured. | `PaymentFundingWorkflowTest` |
| Schedule service purchase | `POST /wallet/scheduled-purchases` — `wallet.scheduled-purchases.store` | `auth`, throttle | `ScheduledServicePurchaseController` validates transaction PIN and creates/looks up schedules by authenticated user plus idempotency key; delete/query operations are owner-scoped. | `ScheduledPurchaseRunnerTest`, `FinancialMutationAuthenticationTest` |
| Purchase/recover VTU order | `POST /wallet/vtu/orders`, `POST /wallet/vtu/orders/bulk`, recover/status/detail routes | `auth`, throttle | `VtuOrderController` scopes recovery, batch status and order detail by current user; durable attempt state prevents resubmitting an uncertain provider outcome. | `MultiProviderVtuRouterTest`, `VtuProviderWebhookRecoveryTest`, `VtuOrderMariaDbConcurrencyTest`, `FinancialMutationAuthenticationTest` |
| Create/delete service beneficiary | `POST/DELETE /wallet/service-beneficiaries` | `auth`, throttle | `ServiceBeneficiaryController` must bind records to authenticated user and scope mutation/query by owner. | Service-beneficiary feature coverage and route auth coverage should be kept in sync when these paths change. |

## Staff and callback mutations

| Operation | Route / name | Guard / service boundary | Required invariant and regression coverage |
|---|---|---|---|
| Approve/reject manual deposit | `POST /admin/manual-deposits/{publicId}/review` | Admin route group requires `auth` + `can:staff.permissions.manage`; controller requires pending/review-required state, actor-specific evidence view, and forbids self-review. | Locked review and ledger idempotency; `ManualDepositWorkflowTest`. |
| Update manual deposit settings | `PUT /admin/manual-deposits/settings` | `auth` + `can:staff.permissions.manage`, throttle | Configuration mutation is staff-gated; review/approval remains separate from customer submission. |
| Approve refund | `POST /admin/payment-refunds/{refund}/approve` | `auth` + `can:refunds.approve`, throttle | Requester cannot approve own refund; locked intent/refund; reserve funds once; provider uncertainty remains review-required and is reconciled, not resubmitted. `PaymentRefundWorkflowTest`, `PaymentRefundReconciliationTest`. |
| Reconcile VTU order | `POST /admin/vtu-orders/{publicId}/reconcile` | `auth` + `can:staff.permissions.manage`, throttle | Staff-only operational action; reconcile the recorded provider attempt/reference and do not create a new purchase on an ambiguous outcome. Provider recovery tests cover uncertain outcomes. |
| Gateway webhook settlement | Provider callback endpoints | Signature/authentication and event deduplication in callback/service path (not a customer session route) | Only verified events can credit; event-ID payload changes/replays rejected; ledger settlement is transactional and safely replayable. `PaymentFundingWorkflowTest`, `PaymentFundingMariaDbConcurrencyTest`. |
| Provider status webhooks | VTU provider webhook endpoints | Provider signature verification plus persisted event deduplication | Do not trust unsigned status, duplicate events, or stale updates to overwrite terminal success. `VtuProviderWebhookTest`, `VtuProviderWebhookRecoveryTest`. |

## Audit findings and remaining verification

- Source review confirms the principal financial mutation routes are session-protected, with separate refund-approval permission and staff-only operational/settings routes. Customer refund, transfer history, payout history, VTU order/batch lookup, scheduled purchases and beneficiary paths have owner-scoped query/service controls in their implementations.
- Reviewed services already implement idempotency/replay checks, wallet/intent/refund locking, ledger posting, payout/refund reservation and uncertain-outcome reconciliation. The peer-transfer service also resolves a unique-key race as a replay or payload conflict after rollback. No additional production-code defect was confirmed in this source-only pass; do not add speculative financial changes.
- Existing dedicated MariaDB independent-worker suites cover funding webhooks, refunds, payouts, peer transfers, wallet balance limits and VTU bulk order processing. SQLite/full PHP CI is useful but is not a substitute for those MariaDB concurrency tests.
- Focused/full test status must be read from the workflow runs for the exact current `main` SHA. A workflow still running is not a pass. The completion register must record terminal conclusions only.
- Live provider behavior, real-money transactions, cPanel production settings, real-device SMS/WhatsApp delivery, and browser/WebAuthn checks on the production HTTPS origin are outside this source/CI audit and remain separate deployment gates.
